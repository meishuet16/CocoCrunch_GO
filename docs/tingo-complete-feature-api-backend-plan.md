# CocoCrunch — Complete Feature, API & Backend Plan

**Purpose.** This is the consolidated build reference for the CocoCrunch product specification, the revised technical build plan, and the existing CocoCrunch codebase. It intentionally describes only each feature, the external API (if any), and the backend capability required to make it real.

## Product and technical decisions

- **Product name:** use **CocoCrunch** in user-facing copy. **Tingo Card** remains the in-product traveller-preference profile.
- **Backend baseline:** **Supabase** — Auth, Postgres, Row Level Security (RLS), Realtime, Storage and Edge Functions in one project. Edge Functions own all provider secrets and webhook verification; the browser never calls paid/private APIs directly.
- **Keep the current domain logic.** The deterministic rules in `src/domain/` remain the product authority: protected Must-Go anchors, hard Deal Breakers, group conflict visibility, atomic Court decisions, tie-only Gacha, minimum-loss repair, explicit learning and privacy defaults. Provider data enriches those rules; it does not replace them.
- **Use current Google APIs.** Implement routing with **Google Maps Routes API `computeRoutes`**, not the legacy Distance Matrix API; use **Places API (New)** for place search/details/opening hours. Cache all provider responses and label any fallback estimate honestly. [Google Routes API](https://developers.google.com/maps/documentation/routes/reference/rest/v2/TopLevel/computeRoutes)
- **AI is proposal-only.** An LLM can suggest, explain, or prepare a diff, but every consequential plan mutation has a preview, confirmation and undo. Group mutations additionally require Court or Emergency Court.

## Existing implementation baseline

The current React/Vite prototype already has local, deterministic implementations of Tingo assessment, trip setup, preference/group-DNA logic, itinerary and Plan Health, budget calculations, Court and tie-only Gacha, backup/repair preview with undo, manual check-ins, privacy/status patterns, packing, memories and explicit preference learning. Persistent state is currently local and prototype adapters are clearly labelled.

The production work is therefore primarily: authenticate and persist source data, add RLS and realtime coordination, replace clearly-labelled demo adapters with server-side provider integrations, and make long-running / push workflows event-driven.

## Shared backend foundation

| Capability | API | Backend implementation |
|---|---|---|
| Identity and membership | None | Supabase Auth; `profiles`, `trips`, `trip_members`. RLS grants members access only to their own trips and assigns `owner`, `editor`, `member` roles. |
| Source state and audit history | None | Supabase Postgres. Persist user inputs, confirmed decisions, consent and pre-repair plan snapshots; re-derive Tingo dimensions, Group DNA, Plan Health and itinerary outputs. |
| Live collaboration | None | Supabase Realtime database changes / presence per trip. Use database RPCs for any contested write (votes, confirmation, planner turn), never client-side read-modify-write. |
| Provider and AI gateway | OpenAI Responses API or Anthropic Messages API; travel/map providers below | Authenticated Supabase Edge Functions with rate limits, validation, caching and provider keys held in project secrets. Supabase Edge Functions are designed for small server-side integrations and webhooks. [Supabase Edge Functions](https://supabase.com/docs/guides/functions) |
| Media and consent-controlled publishing | None | Supabase Storage for original photos and generated assets; signed URLs; `visibility = private` by default and publish/unpublish transactions. |
| Security | None | RLS for every table, function-level user authorization, audit records for plan changes, encrypted provider secrets, webhook signature verification and minimal retention of location-related events. |

## Production invariants to enforce in database and functions

1. **Must-Go never disappears through AI or repair.** It may be surrounded by different floating items, never substituted.
2. **Deal Breakers reject candidates and backups before a vote or recommendation is displayed.**
3. **Group official-plan changes are server-authorized governance events.** Individual drafts and exploration ideas are separate records.
4. **Gacha runs only for a true Court tie; everyday Gacha is a separate data path.**
5. **Provider outage is graceful.** Cache where appropriate and return a labelled estimate/fallback instead of inventing live data or crashing generation.
6. **AI proposes; humans apply.** Every material suggestion includes inputs/evidence, a diff, confirmation and undo.
7. **Privacy is default-on.** Community is private, exact group location is absent, continuous tracking is disabled, and status sharing uses the minimum data required.
8. **Learning is opt-in.** Actual outcomes may create a learning proposal, but only a confirmed action creates a new profile-history snapshot.

## Build order

1. **P0 — demo spine:** Supabase Auth/RLS, trip and profile persistence, Group DNA, deterministic plan/Plan Health, Court/RPC/Realtime/Gacha, Backup Plan, weather-triggered repair preview and confirmation.
2. **P1 — usable travel:** provider-backed routes/places, budget prices/cache, packing/reminders, mood/status/reunion, safety lookup, push action check-ins.
3. **P2 — retention:** photo uploads/map/journal, retrospective and confirmed learning, async Memory Cards, consent-gated Community and limited external-link import.

## Code-to-production migration boundary

| Keep in the existing app | Replace / add behind the boundary |
|---|---|
| `src/domain/tingo.ts`, `preferences.ts`, `group-dna.ts`, `itinerary.ts`, `plan-health.ts`, `court.ts`, `backup-repair.ts`, `budget.ts` and their tests | Local persistence becomes Supabase source-state persistence; local adapters become Edge Function calls with cache/source-status fields. |
| Presentation components, Coco rituals, recommendation-evidence UI and the planning/travelling/completed workspace | Auth session, Realtime subscriptions, provider-backed maps/weather/prices/safety, Storage uploads and consent-publish flows. |
| Existing prototype labels and fallback behaviour | Typed provider responses, retry/error state, stale-data labels, RLS policies, audit logs and webhook verification. |

This preserves the strongest part of the present codebase—the transparent, testable travel-decision rules—while adding only the APIs and backend responsibilities needed for a real multi-user product.
